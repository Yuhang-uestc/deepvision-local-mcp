## 一、环境与安装

### 1. PowerShell 5.1 解析含中文的 .ps1 报"字符串缺少终止符"

【症状】运行 install-extra.ps1 等脚本直接报 ParserError，中文乱码成 `瀹屾垚` 之类，引号被"吃掉"。
【根因】PS 5.1 读取**无 BOM** 的 .ps1 时按 ANSI/GBK 解码，UTF-8 中文被误读，多字节把行尾引号吞掉。
【对策】所有含非 ASCII 的 .ps1 必须存成 **UTF-8 with BOM**；纯 ASCII 的不用管。
【状态】已修复（4 个脚本统一加 BOM），今后新增 .ps1 记得同样处理。

### 2. PowerShell 管道把中文传给 Python 变成 "??"

【症状】`@'...中文...'@ | python -` 里中文全变问号。
【根因】PS 5.1 默认 `$OutputEncoding` 是 ASCII，管道写中文被丢弃；且 Python 默认按 GBK 读 stdin。
【对策】调用前设置：
```powershell
$OutputEncoding = New-Object System.Text.UTF8Encoding($false)
$env:PYTHONUTF8 = '1'
```
更彻底的纪律：**中文参数一律写成 UTF-8 文件再执行**，不走管道。
【状态】已规避；个人终端可永久修复（设置 PYTHONUTF8 用户环境变量 + 修改 $PROFILE）。

### 3. `curl` 在 PowerShell 里被别名成 Invoke-WebRequest

【症状】`curl -L -C - ...` 报"参数 C 具有二义性"。
【根因】PS 把 curl 映射到 Invoke-WebRequest。
【对策】用 `curl.exe` 全名。
【状态】已知；项目内脚本用 `shutil.which("curl")` 不受影响。

### 4. Python 3.13 与 PaddlePaddle wheel 兼容性

【症状】无，但属于高危项。
【根因】PaddlePaddle 对最新 Python 版本的 wheel 支持滞后。
【对策】装 paddle 前先确认 3.13 有对应 wheel；失败时考虑 conda 换 Python 3.11/3.12。
【状态】本机 3.13 实测 paddlepaddle 3.3.1 可装可用。

### 5. 依赖版本连锁变化

【症状】装 paddlepaddle 时 pip 自动把 numpy 2.5.1 降到 2.3.5、把 opencv-python 5.0 换成 opencv-contrib-python 4.10。
【根因】paddle 依赖锁定。
【对策】装完大依赖后**必须回归验证** ultralytics / cv2 / 项目测试，不能想当然。
【状态】已验证 YOLO 检测与 28 项测试全通过；出现 `RequestsDependencyWarning: urllib3/chardet 不匹配` 为无害警告。

### 6. CLIP 必须用 ultralytics 的 fork

【症状】用 PyPI 的 `clip` 包，detect_by_text 报 `clip.tokenize()` 参数错误。
【根因】ultralytics 调用 `clip.tokenize(texts, truncate=True)`，PyPI openai clip 没有 `truncate` 参数。
【对策】装 `git+https://github.com/ultralytics/CLIP.git`；GitHub 不通时走 ghproxy/ghfast 镜像；装完验证 `'truncate' in inspect.signature(clip.tokenize).parameters`。
【状态】已修复（clip 1.0 fork）。

### 7. YOLOE 不只是要 CLIP，还要 mobileclip_blt.ts（530MB）

【症状】装完 clip 后 detect_by_text 报"PytorchStreamReader failed reading zip archive"或下载失败。
【根因】YOLOE 文本编码器是 MobileCLIP TorchScript（`mobileclip_blt.ts`），存在 ultralytics assets release 上，约 530MB。
【对策】服务端已实现：后台下载 + curl 断点续传 + zip 完整性校验 + 多镜像；工具立即返回进度不阻塞。
【状态】已修复；文件约 530~570MB，GitHub 直连可达时最快（实测 17.5MB/s）。

## 二、网络与下载

### 8. GitHub 不可达 / 大文件被镜像截断

【症状】git clone 超时/Connection reset；ghproxy 下载大文件中途断流（实测断在 529MB、90MB 各一次），生成"假完整"的截断文件。
【根因】大陆网络访问 GitHub 不稳；ghproxy 类代理对大文件不可靠。
【对策】
- GitHub release 资源**直连优先**（实测可达，速度 17.5MB/s）
- curl 加 `--retry-all-errors` 断流自动续传
- 下载后做 **zip 完整性校验**（torch 权重都是 zip），坏文件自动重下
- 多镜像 fallback：github → ghfast.top → ghproxy.net
【状态】已修复（服务端 `_asset_mirrors` / `_download_large_file`）。

### 9. 下载进程残留 + 文件锁

【症状】中断长下载后，0 字节/截断文件被 curl 锁住，删除报"正由另一进程使用"；提权产生的进程普通权限杀不掉。
【根因】中断的提权任务留下子进程（curl/python）继续跑，锁住目标文件。
【对策】
- 中断任务后先查残留：`Get-Process | Where-Object { $_.ProcessName -match 'curl|python' }`（按启动时间识别）
- 普通权限杀不掉就 `taskkill /F /PID <id>`，再不行用管理员终端
- 项目内已统一：先清理残留再重试下载
【状态】已遇到并处理；属流程问题，注意长任务中断后必查残留进程。

## 三、性能与速度

### 10. 8B 视觉模型慢的根因：显存挤爆，20% 层跑 CPU

【症状】最小识图 27s；大图详细模式 300s+ 超时。
【根因】qwen3-vl:8b 权重 6.9GB 塞进 8GB 显存，`ollama ps` 显示 20% CPU / 80% GPU 混合，CPU 部分拖慢整体。
【对策】
- 快速模式（默认 4B，未装自动回退 8B）限上下文 4096、精简 prompt
- 顺手带图只用 quick，禁止展开多轮
- 想提速：`ollama pull qwen3-vl:4b`
【状态】已实现 quick/detailed 双模式；实测大图 quick 19s vs detailed 300s+。

### 11. qwen3-vl 设置 num_predict 会返回空输出

【症状】`options.num_predict=200` 后模型返回空字符串。
【根因】Ollama + qwen3-vl 对 num_predict 的行为 bug（实测 num_ctx/temperature 正常）。
【对策】**不要用 max_tokens 限长**，改用精简 prompt 控制输出长度。
【状态】已规避并写入 README。

### 12. 多图：qwen3-vl 一次只认一张图

【症状】传两张图，模型只认第一张，声称"第二张缺失"。
【根因】Ollama + qwen3-vl 一次只处理一张图（多图支持在此模型上失效）。
【对策】已从架构上解决（见 #34）：`analyze_image(file_paths)` 改为逐张分析后合并；明确要求对比时用 `compare_images` 拼图。
【状态】已修复（v2.3.0）。

### 13. 慢的真凶是推理不是工具调用

【症状】误以为"工具调太多"导致慢。
【根因】一次完整闭环 21 分钟里，模型推理占 15~17 分钟，工具调用不足 1 分钟。
【对策】优化重点放在"少调模型、调快模型"，而不是省工具次数。
【状态】结论已确认。

## 四、模型能力边界

### 14. qwen3-vl:8b 定位能力弱

【症状】让它给精确坐标，5 次全失败；但能验证框、描述场景、读字。
【根因】8B 级 VLM 的像素级定位能力不足。
【对策】坐标类任务走 detect_objects / segment_objects / cv_locate，不让视觉模型报坐标。
【状态】架构设计已规避。

### 15. 密集人群数人：遮挡是最大难点

【症状】同一张 20 人合影：YOLOv8=13、视觉模型=16、YOLO-World=19、YOLOE=19、真实=20。
【根因】后排被前排遮挡，框/数数都会漏；低置信度阈值会引入误检。
【对策】优先 `segment_objects` 数掩膜；多模型交叉验证；别信单轮数字。
【状态】结论已确认，属模型能力边界。

### 16. OCR 误读率

【症状】Windows OCR 把"请"读成"讠青"、"图"读成"匿"。
【根因】系统 OCR 对中文/艺术字弱。
【对策】重要文字用 PaddleOCR 并交叉核对；小字先裁切放大。
【状态】PaddleOCR 已接入，实测全对。

### 17. 模板匹配对纯色模板失效

【症状】纯色方块做模板，TM_CCOEFF_NORMED 全图得分 1.0（退化）。
【根因】常数模板导致归一化相关性除零。
【对策】模板必须含纹理/边缘；服务端已加防护提示。
【状态】已修复。

## 五、PaddleOCR 专题

### 18. PaddleOCR 3.x 移除了 use_angle_cls / show_log

【症状】`PaddleOCR(use_angle_cls=True, show_log=False)` 报 `Unknown argument`。
【根因】3.x API 变更。
【对策】构造参数 try/except 降级：2.x 全参数 → 3.x 最小参数。
【状态】已修复。

### 19. Paddle 3.x 的 oneDNN+HPI bug（本项目的重点坑）

【症状】`predict` 报 `(Unimplemented) ConvertPirAttribute2RuntimeAttribute not support [pir::ArrayAttribute<pir::DoubleAttribute>] (onednn_instruction.cc:118)`。
【根因】PaddlePaddle 3.3.1 的 **HPI（新推理引擎）在 CPU 上自动选择 oneDNN 后端**，该路径存在 bug。
【教训】
- 先试的 `FLAGS_use_mkldnn=0` 环境变量**无效**——HPI 的 backend 选择不读这个 flag
- 正确解法：构造 PaddleOCR 时显式指定
  `engine="paddle_static"`、`enable_hpi=False`、`enable_mkldnn=False`
【状态】已修复并实测通过（识别+坐标全部正确）。

### 20. PaddleOCR 静默回退掩盖错误

【症状】engine=auto 时 Paddle 报错会被吞掉，静默回退 Windows OCR，用户以为没问题。
【根因】auto 分支未暴露错误。
【对策】回退时把失败原因拼进返回结果；显式 engine=paddle 可强制看真实报错。
【状态】已修复。

### 21. PaddleOCR 需要写 ~/.paddlex

【症状】受限沙箱里报 `Permission denied: C:\Users\Administrator\.paddlex\...`。
【根因】模型缓存与临时文件在用户主目录。
【对策】运行环境需对该目录可写；Codex 正常（非沙箱）运行无此问题；首次调用会从 modelscope 下载模型（100MB+）。
【状态】已知事项。

## 六、工程与流程

### 22. 长任务无进度反馈，用户以为卡死

【症状】下载 530MB 或长推理期间，界面静止 10~20 分钟。
【根因】同步工具调用拿不到中间结果。
【对策】
- 服务端：大文件下载改**后台线程**，工具立即返回"下载中/当前 xxMB"
- 协作端：启动长任务前先发进度说明
【状态】已修复（`_start_model_download` 后台下载 + 进度返回）。

### 23. 先斩后奏：有取舍的决策要先问

【症状/教训】禁用 oneDNN 的代码先改了、再申请验证，用户质疑"万一删文件怎么办"。
【根因】顺序错误：决策性改动应先确认后动手。
【对策】凡是"有取舍的决策"或"删除/移动"操作，先给方案、等确认再改；删除类必须列明确切目标。
【状态】已达成共识。

### 24. 沙箱权限分层

【要点】workspace-write 只允许写工作区；read-only 连工作区都写不了；提权通道有时被策略自动拒绝。操作前先判断目标路径是否在工作区，避免白跑。
【状态】已知约束。

### 25. 下载完整性校验是刚需

【要点】torch 权重/onnx 都是 zip 格式；下载后必须 `zipfile` 校验中央目录，截断文件直接重下。
【状态】已实现。

### 26. 工具列表重启才生效

【要点】MCP 工具列表在 Codex 启动时加载；新增/修改工具后必须重启 Codex，否则用的是旧 server。
【状态】已知事项。

### 27. 输出安全

【要点】`VISION_OUTPUT_DIR` 可限制生成文件目录；默认禁止输出覆盖输入图；config.toml 含 API Key 绝不入库；.gitignore 排除权重/真人照片/缓存。
【状态】已实现。

## 七、本轮（课表识别）新增观察

### 28. 大图 + 详细模式 = 超时

【症状】1680×1260 课表截图，detailed 模式 300s 超时无结果；同图 quick 模式 19s 出概览。
【根因】大图 + 8B 详细输出，token 生成太长。
【对策】大图优先 quick；需要细节就裁切局部放大后 detailed。
【状态】观察结论，建议写进 skill：超过 ~1500px 宽优先 quick + 局部裁切。

### 29. OCR 坐标即结构化数据源

【要点】PaddleOCR 的坐标框可以把表格类图片转成结构化数据（本轮的课表就是靠坐标重建了课程-教室对应）。这类"OCR 先行、视觉模型后补"的流程值得固化为模板。
【状态】正向经验。

## 八、同类项目调研与健壮性升级（v2.2）

### 30. 同类项目调研心得（2026-08-07）

对 GitHub 上十余个视觉 MCP 项目做了横向调研（vision-primitives-mcp、vision-bridge-mcp、VisionPower、llm-vision-mcp、mcp-vision-bridge 等），可借鉴点：

【防提示注入】图片内容（尤其 OCR 文字）可能是恶意指令，输出必须带"不可信数据"前缀——VisionPower 的做法，已采纳。
【结果缓存】vision-bridge 按"图+模式+问题"哈希缓存；VisionPower 进程内缓存（TTL 30min）。本地 8B 一次 20~60s，缓存收益极大——已采纳。
【重试与退避】llm-vision-mcp 对 429/5xx/网络错误指数退避重试；404（模型缺失）不重试——已采纳。
【诊断工具】vision_health / vision_status 一键看配置与连通性，大幅降低排障成本——已采纳。
【粘贴图片落盘表】mcp-vision-bridge 整理了各客户端粘贴图片的存放位置（Claude Code / opencode / Codex 等），已写入 README 兼容性章节。
【宿主超时】VisionPower 建议 MCP 客户端超时调到 120s 以上（本地推理慢），已写入 README。
【验证过的设计】vision-primitives 的消融实验证明"粗定位→裁切→精定位"能把定位误差从 208px 压到 0~3px（分辨率稀释问题），与本项目 skill 的"大图优先 quick + 局部裁切"思路一致，等于外部验证了我们的做法。
【暂不采纳】云端模型预设（本项目定位是本地优先）、WebUI 配置台、URL 输入（无 SSRF 需求）、路径白名单（本机用户场景风险低）。

### 31. v2.2 新增：缓存 / 重试 / 不可信前缀 / vision_status

【实现】`_cache_*` 进程内缓存（内容 SHA-256 + 参数做 key，TTL 默认 1800s、上限 64 条、按内容哈希保证文件替换后失效）；`ollama_generate` 对 429/5xx/网络错误指数退避重试（`LOCAL_VISION_RETRIES` 默认 2）；`untrusted_ok()` 给 analyze/OCR 返回加前缀；`vision_status` 输出配置+依赖+Ollama 连通性。
【实测】真机验证：4B 快速模式首次 33s，二次同参数调用 0.00s 命中缓存且结果一致；OCR 返回带前缀。
【状态】已实现并通过 28 项离线测试 + 真机冒烟。

### 32. PaddleOCR 报 Permission denied / 自动回退的根因（重要）

【症状】`ocr_extract` 报 `Permission denied: ~/.paddlex/official_models/UVDoc/inference.yml` 后回退 Windows OCR。
【根因排查】不是 PaddleOCR 的普遍问题，而是**运行账号与缓存目录归属账号不一致**：PaddleX 缓存默认 `~/.paddlex`，
目录由下载模型的账号创建；换账号（Windows 多用户 / 沙箱账号 / 服务账号）运行时，新账号对该目录无写权限，
就会在写 `inference.yml` 时 Permission denied。本项目开发沙箱账号（codexsandboxoffline）复现了该症状；
真实用户账号下 PaddleOCR 正常工作。另外 PaddleX 用 `filelock` 做并发下载锁，多个进程同时首次初始化也会互相踩锁。
【对策】
1. 用与下载模型时相同的 Windows 账号运行（正常桌面场景不受影响）；
2. 缓存目录重定位到有写权限的位置：`setx PADDLE_PDX_CACHE_HOME "D:\paddlex_cache"`（改完重启 Codex）；
3. 服务端已加 `_PADDLE_OCR_INIT_LOCK` 串行化初始化，避免同一进程内并发首次初始化互相踩锁；
4. 仍异常时删除 `~/.paddlex`（或其中失败的模型目录）重新下载。
【状态】已定位并修复（并发锁）；文档已补充 PADDLE_PDX_CACHE_HOME。

### 33. 输入校验与可选大图缩放（含 fallback 链评估结论）

【评估】模型 fallback 链（`OLLAMA_VISION_MODELS=a,b,c` 逗号分隔）：本地通常只装 2 个视觉模型，已有 quick→detailed 404 回退覆盖主要场景，
暂不引入，避免配置面膨胀；未来真装了多个视觉模型（如 llava / qwen2.5-vl 备用）再补不迟。
【实现】`_validate_input_image`：主要看图工具（analyze / image_info / ocr / crop）拒绝相对路径、按 magic-byte 校验真实格式（扩展名仅供参考，内容合法即接受；扩展名与内容不符时 `image_info` 会输出提示，不拦截——因为下载/转存图片扩展名经常是错的，硬性拦截会误伤正常文件）；
`LOCAL_VISION_MAX_DIMENSION`（默认 0 关闭）让 analyze 超长边大图发送前自动等比缩小（Pillow LANCZOS，转 RGB 输出 PNG）。
【权衡】整图缩放必然损失全局细节，故默认关闭、仅作"防卡死"兜底；要精度的路径是"crop 局部放大后 detailed"，不受缩放影响。
【状态】已实现，28 项离线测试通过。

### 34. 多图策略：默认逐张，明说对比才拼图（v2.3.0）

【决策】用户多图场景的大头是"每张都要看"，对比是少数。因此：
- `analyze_image(file_paths=[...])` 多图时**逐张独立分析**（每张完整看），结果带"图1（文件名）…"标签合并返回；
- 新增 `compare_images` 工具：仅当用户明确要求"对比 / 有什么区别 / 哪个更好"时使用，把多图按图1/图2…拼成网格、一次分析异同。
【实现】`_analyze_images`（逐张合并）+ `_montage_images`（Pillow 拼图 + 微软雅黑标签）+ `call_compare_images`；`handle_tools_call` 注册；工具数 11 → 12。
【权衡】拼图必然缩小单图、损失细节，所以拼图只服务"对比"场景，细节仍走逐张分析。
【状态】已实现（30 项测试通过），README / skill / 架构文档同步更新。

### 35. 边界测试审计：EXIF / 颜色 / 内存保护等（v2.3.0）
